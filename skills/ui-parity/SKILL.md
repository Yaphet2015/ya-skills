# UI Parity

把“和另一处一致”转成可检查的行为约定。用于现有页面、弹窗、选择器等 UI 的对齐和公共组件抽取。完成依据是用户可见的对照结果。

## 确认对象和范围

先读需求、相关会话、实际入口和调用方。用户给出会话链接时，先用可用的会话工具恢复上下文。

- 确认基准界面、待对齐界面及各自的打开路径。名称相近时，核对按钮、页签和组件；例如“分享”与“分享详情”可能是两个入口。
- 确认要求覆盖布局、状态、交互，还是完整流程。只有布局要求时，不自动改写全部业务控制逻辑；要求复用完整选择器时，需检查它的输入、粘贴、选择、移除和键盘处理。
- 跟踪用户后续补充。新增页签、调用方或交互要求时，更新检查范围和完成条件。
- 搜索公共组件的直接和间接调用方。抽取影响到的现有使用方都需要回归检查。

简短复述基准、目标、必须一致的范围，以及允许保留的业务差异。用已给出的决定消除疑问；只有入口或关键预期仍不明确时，才问一个具体问题。

## 改动前记录基准

记录基准版本、目标版本和工作区改动。未提交内容属于基准的一部分，单独记下；不能只用 HEAD 标识它。优先保留当前基准的渲染和交互证据，再开始抽取。

建立一份持续更新的对照表。放在现有任务记录或项目指定的产物目录；项目无约定时，可使用系统临时目录并提供绝对路径。每项包含：

| 项目 | 必须记录的内容 |
| --- | --- |
| 场景 | 界面、页签、初始状态、数据和操作顺序 |
| 预期 | 要一致或要保留的结果，以及需求或基准证据来源 |
| 允许差异 | 业务理由和用户决定；未确认的差异保持待确认 |
| 回归结果 | 旧版本与改后版本的对照、证据、状态 |
| 对齐结果 | 改后基准与改后目标的对照、证据、状态 |

状态使用“通过／失败／未验证”。不适用的场景写明理由。不要把代码中现存的差异直接列为允许差异。

按实际组件选择状态和操作，读取 [references/scenarios.md](references/scenarios.md) 补齐容易遗漏的路径。保留稳定的场景 ID，后续反馈继续补到同一张表中。

## 按交互责任抽取

检查状态由谁持有、事件由谁处理，以及各调用方是否仍各自实现了需要统一的行为。

复用完整交互时，公共边界应覆盖相关的状态转换。例如选择器的查询文本、原生粘贴、异步校验、选中项、移除和关闭原因，需要共同维护一致的约定。可用组件、hook 或控制器实现，按现有架构选择。

接口、权限、期限、审批等业务规则按约定保留在适当的适配层。不要为了消除业务差异不断增加行为开关。也不要仅因用了同一个组件名，就认定输入和状态处理已经一致。

抽取会影响事件顺序和焦点。核对关闭事件的阶段、关键词清理时机、Esc 传播、候选项是否可聚焦，以及 Portal 与弹窗焦点范围的关系。按本次需求保留或修改这些行为，不把某个旧实现的细节推广为所有组件的规则。

## 做两组对照

**回归：旧版本 ↔ 改后版本。** 检查基准及其他受影响的现有使用方。对要求保留的行为做对照；有意改变的行为关联到明确需求。

**对齐：改后基准 ↔ 改后目标。** 使用相同或可对等的数据、视口、缩放、字体、主题和请求状态，执行相同操作。比较结果与允许差异表。

两组对照分别给出结果。两个改后界面一起出现相同错误，仍可能通过对齐检查，因此不能省略旧版回归。旧版运行不了时，记录可取得的代码或历史证据，并把依赖真实运行的项标为未验证。

### 选择足够的证据

| 要证明的内容 | 需要的证据 |
| --- | --- |
| 高度、间距、溢出、标题和状态区 | 实际渲染截图及相关元素测量；记录环境和状态 |
| 输入、粘贴、选择、移除后的可见结果 | 经过实际控件的操作，以及操作后的文本、标签和候选列表 |
| 关闭时机、Esc、Tab、焦点与 Portal | 运行环境中的事件顺序、焦点路径和可见结果 |
| 业务适配仍正确 | 相关调用方的集成检查、请求或回调证据 |

优先在真实应用中检查。可用加载真实组件的运行环境控制数据和时序，但需保留相关的样式、Provider、Portal、焦点管理及事件路径。手写的仿制页面不能证明真实组件正确；隔离环境缺少的应用条件要明确列出。

粘贴检查应经过控件的实际粘贴路径，观察原生输入效果和异步结果。直接调用 `paste()` 控制器方法，只能证明该方法。合成 DOM 事件也不能单独证明系统剪贴板和原生默认行为；工具无法执行的部分标为未验证。

按需求或基准确定尺寸预期和容差，不临时放宽标准。要求状态间高度一致时，要同时检查加载、空、错误和有数据的相关状态；不要直接设置固定高度来掩盖正文结构差异。

类型、格式、构建和单元测试提供辅助证据。保留能防止实际行为回归的测试；测试数量不构成 UI 对齐证明。记录临时检查的脚本或具体步骤和结果，使后续复核可执行。

## 发现遗漏后检查同类路径

用户报告新差异时，先用报告中的正常路径复现。可能解释现象的特殊情况只能作为假设；例如“过滤当前账号”不能解释其他账号也无法粘贴。

修复后，检查同一状态或事件责任范围内的相邻场景，并重跑受影响的两组对照：

- 粘贴差异：检查输入保留、分隔符、校验期间输入、候选选择、移除后重新输入。
- 高度差异：检查状态区、标题条件、最小高度、换行和滚动。
- 关闭或焦点差异：检查外部操作、Esc、重新展开、Tab 和 Portal。

已有多处同类差异时，重新检查公共边界是否仍保留两套通用处理逻辑。扩查到有因果关系的范围，完成后更新对照表。

## 用证据决定完成

必需场景仍失败或未验证时，继续处理可执行的工作。遇到缺少运行环境、账号或工具能力等实际阻塞时，交付已完成的改动、阻塞场景和补齐证据所需的最小步骤，明确写“对齐验收未完成”。不要把代码检查通过写成“全部对齐”或“原功能未受影响”。

最终报告简短说明改了什么、允许哪些差异、两组对照各自的结果及证据位置。把“代码已实现”和“对照已验证”的结论分别写清。只有必需场景都有足够证据并通过时，才报告对齐完成。
