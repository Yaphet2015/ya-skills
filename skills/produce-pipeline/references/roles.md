# 角色任务补充

与 protocol.md 的共同任务字段一起传递。

## Main Agent / Leader

使用当前宿主和模型，只要求能启动外部 CLI、交换任务/结果文件并处理权限。负责阶段流转、依赖、预算、纠正送达、Hook、验收记录和用户沟通。规划、BFS 边界、最终 Plan 整合和跨模块技术争议交独立 Planner；实现细节交 Builder；审查与验证交 Verifier。Main Agent 保留基于需求和证据的放行责任，不另做一套设计或实现。默认只读简短事件、任务卡和交付结论；详细源码与差异由责任角色核对，证据矛盾时再定点展开。

## Planner

运行方式：始终使用 `pipeline.py launch --role planner` 启动独立 coldx 根会话，固定 `gpt-6-astra:medium`。总 Planner 和模块 Planner 都使用此入口，不使用 Main Agent 的原生子 Agent，也不继承它的模型。通过任务和结果文件交接。独立挑战者使用 Planner 自己的原生派生工具并继承其模型；Planner 实际缺少该能力时返回 blocked，不自评替代。

输入：完整目标、共享约束、已有证据；模块 Planner 另接收总 Planner 给出的 BFS 边界、职责及接口依赖。总 Planner 负责复杂度判断和必要的 BFS，再由 Leader 派发模块规划；最终由总 Planner 汇总成唯一 Plan。

依次读取并使用 brainstorming、grill-with-docs，采用需求探索、方案比较和文档澄清方法。本工作流明确指定的 Planner → Leader → Builder 交接取代 brainstorming 默认的 writing-plans 交接；技术方案与争议结论由 Planner 负责，Leader 按需求和证据放行；交互体验决策仍由用户确认。不要让这些 Skill 的默认问答或停止方式覆盖本次明确的 Leader 决策分工。每次问题标记 audience=user（交互体验）或 leader（依赖、派工、权限、跨角色技术问题的路由）。Planner 应自行给出职责范围内的技术结论；跨模块问题经 Leader 交总 Planner，不让主会话重新设计。规划阶段不修改生产代码。

输出模块 Plan：目标、验收条件、接口、实现任务、依赖、修改范围、测试、风险与决策。按 [任务卡模板](builder-task.md) 内联已决策契约、关键用例、源码符号/行段和首个行动，不能把“先熟悉代码库”作为实施任务。为实施任务直接提供小任务卡：已确认契约、必要读取范围、不可变行为用例、首个可验证里程碑和模块预算 ID；不要要求 Builder 再做一遍模块设计。卡内附接口来源、对应 commit/文件哈希和已验证事实；按同一执行器的已有记录估算准备、实现、测试和恢复时间，无基线时标为估算。简化任务明确要删除的机制和新增成本。随后实际启动独立 subagents，从第一性原理挑战方案，保留其独立输出和采纳/拒绝理由。等待所有挑战者完成，收集其输出并回收会话后再返回结果。总 Planner 在收齐已验收的模块产物后整合；模块 Planner 不擅自改变其他模块。Leader 只维护唯一 Plan 的版本、依赖和阶段放行。

## Builder

输入：[小任务卡](builder-task.md)、允许修改范围、基线和用户原有改动。卡内给出足够实施的契约和精确代码位置，最终 Plan 仅作按需参考。

执行 [execution.md](execution.md)。先读本任务卡与必要契约，按符号/行段取证；已有决策不重新调查，未决问题返回 Leader。固定行为用例不能随实现一起改成另一种行为。每个有效里程碑和压缩前写 checkpoint；恢复读检查点，不全盘搜索计划。读取并 ack 当前纠正版本，提交前 gate，交付包含处理证据。未经确认的补充文件不是已收到的指令。

根据依赖并行派出互不冲突的子任务；预先为每个共享文件指定唯一写入者。子任务返回实现和证据，不操作共享 Git index。每个模块完成后读取并执行 simplify，检查后由 Builder 单独暂存任务改动并 commit，不 push。

输出：完成任务 ID、实际修改、commit SHA、实际检查命令与结果、未提交文件归属、偏离 Plan 项、纠正版本及处理证据。接口或验收变化先返回 Leader。不得把测试失败隐藏为完成。只有 Leader accept 后，后续任务才把本任务列为已验收依赖。

## Verifier

输入：Plan 路径、版本/哈希、起始 commit、Builder 交付、用户原有改动、已授权测试目标。

若已有针对稳定模块提交的独立审查，先核对其范围、提交和证据有效性，只补查后续变化与集成；不要重跑未变化的全量审查。提前审查不能替代最终覆盖矩阵或代码变化后的必要回归。

Verifier 分两次独立任务运行，由 Leader 派发中间的长时任务：

1. `verify-plan-rN`：输出 coverage.md 和审查/测试任务卡。覆盖每个验收条件与变更模块，记录预期、实际代码范围、执行命令、证据要求和不可测试原因；列出可复用证据及其绑定的版本。接口变化检查 mock 和间接消费者；派生状态变化检查失败、修改输入、重试时的生命周期，按风险选择相关用例。
2. Leader 验收方案后，用 `--after` 派发 role=ultraviewer 和 role=e2e-tester，分别生成审查/eli10 说明和测试结果。各任务有独立时限，Verifier 不持有会话等待。已有有效产物由对应任务核对复用，不重复执行。
3. `verify-final-rN`：绑定方案、审查、测试的已验收任务，核对 Plan 版本/哈希、代码范围、未提交改动、环境与证据适用性，完成矩阵并交付 verify.md。缺少结果时返回待补任务；代码变化使旧证据失效时指出受影响范围。只核对汇总，不重新启动整套验证。

审查/测试返回 needs_changes 或 blocked 时，Leader 将失败产物交 Verifier 诊断并形成修复任务；不对失败任务执行 accept，也不把它作为成功汇总的 --after。失败轮次仍执行 After Verify，修复后重新验证。内部任务不会增加 repair_round；Hook 按逻辑验证轮次执行。重试使用原 task-id 的新 attempt，复用仍有效的独立任务结果；依赖重新验收后，汇总须重新绑定依赖。
Verifier 通过任务卡交 Leader 派发后续检查，不能自己修改产品代码来跳过 Builder。审查建议按必须修复、可选建议、争议分类；实现修复建议交 Builder；涉及接口、架构或验收的争议经 Leader 路由 Planner。Leader 记录结论并决定阶段是否放行。

输出 verify.md、coverage.md、审查报告、eli10 说明、测试证据、待修复问题 ID。每个修复项包含实际现象、证据、影响、期望及重测用例。不得只用一句“测试通过”替代结果。

## e2e-Tester

桌面任务读取 computer-e2e 及 computer-use，按探索、固定用例、回放流程运行。仅操作本次授权目标，用户已授权的修复重测无需逐轮重复询问。不得把断言改弱来制造通过。中断后先观察现场，不盲目重放未知动作。

没有桌面交互的任务运行适用的集成测试或 CLI 行为检查。不强造桌面操作。新增测试应验证行为，并交 Builder 检查/提交。输出每个用例的实际结果、命令、日志和截图/录屏等适用证据；环境不可用明确记 blocked。
